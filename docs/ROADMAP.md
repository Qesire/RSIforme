# 构筑顺序与验收

每一阶段以实际运行产物验收。代码存在、配置通过解析、完整任务成功和取得算法收益分别记录；后续阶段不借用前一阶段的完成状态。

## 0. 本地最小闭环

用 JSONL 聚合任务验证候选归档、独立执行、质量失败、结果绑定、最好版本恢复和复测交付。预置 baseline、incorrect、optimized 三个实现，让错误实现确实被评价器拒绝，恢复时检查文件内容身份。保留运行环境、原始测量和退出状态。

这一步建立可运行的工程骨架。候选预先写好，吞吐来自 CPU 示例；其通过不代表 Agent 已经自主发现优化，也不代表生产任务接入成功。具体本轮验证结果以仓库根目录的实施记录为准。

## 1. 绑定一个真实任务与站点

选择已有完整基线、输入和验收程序的推理任务。填入真实 Slurm 分区、账户、共享目录、镜像和 A100 资源；先用 Harness dry-run 检查配置，再执行 oracle。绑定任务允许修改路径与归档目录，验证 Work 中的候选能对应到主机侧的 run/round 结果。

验收资产是成功的基线作业、完整日志、评价 JSON、环境记录，以及恢复后重新运行的同一候选。H100 参考数据不进入 A100 的性能比较集合。任务或依赖尚未到位时，将缺口记入运行记录，保留本地已完成能力。

## 2. 一个 Agent、一条研究线

让编码 Agent 读取 [program.md](../program.md)，依据基线 profiling 选择方向。至少完成一次有真实作用机制的修改和一次完整评价；失败诊断应影响后续动作。候选在提交前归档，返回的 round 绑定到唯一源码版本。

验收包含一次会话或任务中断后的继续，以及恢复一个早于最终工作区的候选。结束时提供准确差异、运行命令、质量与性能结果、资源消耗和未解决的问题。自动提交次数和资源预算由任务实测成本决定。

## 3. 多研究线与组合

在单线可靠后增加少量独立方向，各自固定父代和预算。比较采用同一任务合同，合并不同改动后再做完整测量。先确认并行能减少等待或提高单位预算的有效候选数，再增加执行器；单控制器继续负责发布。

## 4. 改进研究方法

积累足量真实轨迹后，比较父代选择、历史读取、故障定位和方向分配策略。固定任务分布与总资源，测量新策略的有效候选率、最终效果和研究成本。在未参与策略调整的任务上检验迁移；一次任务上的改进不能直接视为研究能力普遍提升。

这一阶段才讨论递归改进：新的研究方法必须产生可复测的下游收益，并保留原研究器作为可恢复对照。
